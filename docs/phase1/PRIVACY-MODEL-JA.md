# 匿名・仮名運用モデル

## 1. 目的

成果物の有用性と検証可能性を保ちながら、実名、住所、所属、既存SNS、個人メール、既存活動との不要な関連付けを避ける。匿名性は一度の設定ではなく、文書、Git、ホスティング、ネットワーク、決済、投稿内容を通じた継続的な運用課題である。

## 2. 基本方針

- 本名、住所、勤務先・所属、個人メール、既存SNSを公開しない。
- 個人の研究、栽培、取引、所在地等と安易に関連付けない。
- プロジェクト専用の仮名、連絡先、公開プロフィールを使う場合も、再利用による横断追跡に注意する。
- DIDはユーザー承認前に掲載しない。公開DIDも他の識別情報との結合で再識別の手掛かりになり得る。
- 秘密鍵、seed、復旧情報、署名用パスフレーズをプロジェクト、Git、AI入力へ含めない。

## 3. Gitに関する注意

Gitコミットには `user.name` と `user.email` が記録される。将来公開する前に、リポジトリ単位の設定、過去コミット、署名情報、リモートURLを確認する。

確認例（実行はPhase 1対象外）:

```powershell
git config --local --get user.name
git config --local --get user.email
git log --format='%h %an <%ae>' -n 5
git remote -v
```

仮名メールを使っても、同じメール、署名鍵、ユーザー名、コミット時刻、文体を別活動で再利用すると関連付けられる可能性がある。既存履歴の書き換えは破壊的になり得るため、公開前に別途計画・承認する。

## 4. 二種類の匿名性

### 公開上の匿名性

一般閲覧者に実名や既存活動を直接示さないこと。仮名、専用プロフィール、情報最小化で改善できる。

### サービス運営者からの技術的匿名性

ホスティング事業者、Gitサービス、メール、CDN、SNS等がIPアドレス、端末情報、時刻、決済、ログイン履歴を保持し得る。公開上匿名でも、運営者に対して匿名とは限らない。

完全匿名は保証できない。法的要請、アカウント復旧、漏えい、ログ相関、文体分析、時刻パターン等で関連付けられる可能性がある。

## 5. KYCの可能性

将来、トークン受領、ウォレット、取引所、報酬、税務、法域要件によりKYCが必要になる可能性がある。KYCが必要な場合、公開プロフィールへ実名を掲載する必要があるとは限らないが、サービス提供者には本人情報が渡る。要件と情報共有範囲を確認し、推測で個人情報を提出しない。

## 6. 情報分類

| 区分 | 例 | 取扱い |
|---|---|---|
| 公開可能 | プロジェクト名、一般的な設計思想、監査プロトコル、匿名化したテストケース、ライセンス、非公式である旨 | 内容とメタデータを確認後に公開候補 |
| 承認後のみ公開 | 公開DID、仮名、専用連絡先、署名済み成果物、Git履歴、公開日時、外部アカウントとのリンク | ユーザーが対象・目的・期間を明示承認した場合のみ |
| 非公開 | seed、秘密鍵、復旧情報、パスワード、APIキー、個人メール、本名、住所、所属、端末内パス、IP・アクセスログ、未匿名化の相談文 | 読み取り・保存・共有・Git登録を行わない |

## 7. 公開前チェック

- [ ] ファイル本文と履歴に本名、ユーザー名、メール、実DID、秘密情報がない。
- [ ] スクリーンショット、ログ、絶対パス、画像メタデータを確認した。
- [ ] Gitのauthor、committer、署名、remoteを確認した。
- [ ] 他のSNS・研究・取引活動と不要に結び付けていない。
- [ ] 公開DIDを使う場合、対象成果物と関連付ける範囲を承認した。
- [ ] ホスティング事業者が取得する技術情報を理解した。
- [ ] 削除してもキャッシュ、fork、アーカイブに残り得ることを理解した。
